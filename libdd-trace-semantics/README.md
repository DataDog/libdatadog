# libdd-trace-semantics

The trace semantics registry: which span attributes hold the same concept across Datadog and
OpenTelemetry conventions, and in which order to read them. It is the registry the Trace Agent
uses (`pkg/trace/semantics`), so spans resolve the same way in libdatadog and in the Agent.

```rust,ignore
use libdd_trace_semantics::{lookup_str, Concept};

// The first non-empty value among `http.request.method` and `http.method`.
let method = lookup_str(&span, Concept::HttpMethod);
```

Promoted tags (e.g. `span.kind` or `_dd.origin`) live in dedicated fields, so lookups can't read
them. Use the `Span` and `TraceChunk` getters instead.

## mappings.json

`mappings.json` is generated by Semantic Core and must not be edited by hand. It is a byte for byte
copy of `pkg/trace/semantics/mappings.json` in
[datadog-agent](https://github.com/DataDog/datadog-agent), and `metadata.git_commit` records the
Semantic Core commit it was generated from. To update it, replace the file with the Agent's copy
and run the crate tests. Automated update PRs from Semantic Core will replace this manual step.

At build time, `build.rs` validates the file and compiles it into constant data, so nothing is
parsed at runtime and an invalid file fails the build. Updates reach users with the next
libdatadog release.

The library only says where a concept is stored. It never renames attributes, and keys chosen by
users or operators (filters, additional metric tags, peer tag lists) should be read by their exact
name, not through the registry.

# libdd-ai-usage-ffi

A C interface to [`libdd-ai-usage`](../libdd-ai-usage), so that an LLM gateway
or integration in any language emits the same usage and cost metrics from the
same provider responses: Go through dlopen, Lua through LuaJIT's FFI, Python
through ctypes or a native module. Rust callers use `libdd-ai-usage` directly.

The header is [`include/ai_usage.h`](include/ai_usage.h), generated by cbindgen.
The crate builds a `cdylib` and a `staticlib`, and depends on nothing but
`libdd-ai-usage` and `serde_json`, so it can be built and loaded on its own.
The artifacts are named for the C prefix: `libdd_ai_usage_ffi.so`
(`libdd_ai_usage_ffi.dylib` on macOS, `dd_ai_usage_ffi.dll` on Windows) and
`libdd_ai_usage_ffi.a`.

## Conventions

- Structured values are UTF-8 JSON. Every input is a pointer and a length. The hot DogStatsD
  path also has a text form with no JSON: `_dogstatsd_lines` writes one observation's lines
  separated by `\n`, and `_pack_dogstatsd_lines` / `_batch_take_dogstatsd_text` write datagrams
  (lines joined by `\n`) separated by a NUL byte, with no trailing NUL. On failure these
  functions still write the JSON error.
- Output is written to a `ddog_ai_usage_Buffer` the caller passes by pointer and releases with
  `ddog_ai_usage_buffer_drop`. No structure is passed by value.
- Every call returns a `ddog_ai_usage_Status`: `OK`, `REJECTED` (the input broke a rule; a JSON
  output holds `{"error": {"code", "message"}}` with a stable code) or `INTERNAL` (a null
  pointer, or a panic that was caught; a panic never crosses the boundary).
- Numbers in JSON are IEEE 754 doubles, read and written as the shortest text that round-trips.
  A caller's encoder must write doubles with up to 17 significant digits, or a cost or duration
  arrives as a nearby value, not the one measured. LuaJIT's lua-cjson defaults to 14 digits
  (OpenResty's to 16): call `cjson.encode_number_precision(17)` before encoding a request. Token
  counts are whole numbers up to 2^53 - 1 and are exact at any precision that writes them in
  full; a count written in exponent form (`1e+15`) is still read as a whole number.
- As in the rest of libdatadog, the C ABI carries no backward-compatibility guarantee across
  releases: pin a version.

## Functions

| Function | Does |
| --- | --- |
| `ddog_ai_usage_project` | One observation (`{profile, observation, deployment_attributes, metrics}`) to its Datadog series and issues |
| `ddog_ai_usage_dogstatsd_lines` | One observation (the same request document) to its DogStatsD lines as `\n`-separated text: this observation's alone, never merged with another's, ordered by name then tags |
| `ddog_ai_usage_pack_dogstatsd_lines` | `\n`-separated lines and comma-separated constant tags to NUL-separated datagrams of at most a given size, with no JSON either way. A line longer than the size with its tags is dropped (the Agent refuses it) and counted in the optional `dropped_lines` |
| `ddog_ai_usage_batch_new` / `_add` / `_is_empty` / `_len` / `_take_dogstatsd` / `_take_dogstatsd_text` / `_drop` | Collect projections over an export window and take them as DogStatsD datagrams of at most a given size, with constant tags (`_text`: NUL-separated, no JSON). Lines longer than the size are dropped and counted (`dropped_lines` in the JSON, an optional out-parameter for `_text`). `_len` is the number of points held (one per Counter series, one per Histogram sample; the lines taken can be fewer, never more), for a flush threshold |
| `ddog_ai_usage_batch_set_max_len` / `_dropped` | Bound a batch to a number of points (0 lifts it). An observation that does not fit is dropped whole: `_add` still returns `OK` with `"dropped": true`, and `_dropped` counts it. The count only grows (taking keeps it and the bound), so report the difference at each flush |
| `ddog_ai_usage_parse_provider_response` | A whole provider response body (JSON, or buffered server-sent events) to the observation's usage members, the model and service tier, how it ended and its `error.type` |
| `ddog_ai_usage_stream_new` / `_feed` / `_finish` / `_drop` | The same for a stream read as it passes through, in chunks that may end anywhere. Strings longer than 1 KiB (generated text) are cut as they pass, so a line holding a whole response, such as Responses' `response.completed`, keeps its usage without being held. `[DONE]` ends only OpenAI-shaped streams. Anthropic's `message_start` output count is a placeholder and is not reported: only `message_delta` reports output, so a stream cut before it has no output count to mistake for a reported one |
| `ddog_ai_usage_stream_feed_event` | One server-sent event the caller already split (its `event` name, possibly empty, and its `data`), read as `_feed` reads it; the two can be mixed on one stream |
| `ddog_ai_usage_provider_name` | A gateway's or SDK's provider name to `gen_ai.provider.name` |
| `ddog_ai_usage_error_type` | An error name and HTTP status to `error.type`. A three-digit name is read as a status only when no status is given, so the response's status wins |
| `ddog_ai_usage_error_type_known` | The same without the fallback: `REJECTED` for a name the vocabulary does not know and no failed status, which `_error_type` writes as `api_error` |
| `ddog_ai_usage_provider_ids` | Provider response headers and Bedrock model ARNs to the account and project attributes. Without a `provider_name`, every known header and ARN is tried. Values are trimmed of surrounding whitespace, which is not part of an HTTP field value |
| `ddog_ai_usage_provider_id_headers` | The lower-case response header names `_provider_ids` reads for a provider (all providers for an empty name), so a gateway fetches exactly those |
| `ddog_ai_usage_pack_dogstatsd` | DogStatsD lines to datagrams (JSON form), with `dropped_lines` |
| `ddog_ai_usage_known_metrics` | The metric names of a profile, or of every profile for an empty one: what a request's `metrics` list can keep |
| `ddog_ai_usage_datadog_tag_value` | A value as Datadog stores it in a tag |
| `ddog_ai_usage_is_service_tier` / `_is_deployment_value` / `_is_person_identifier` | The grammars of a service tier, a deployment attribute value and `user.id` |

Observations follow the profiles of the Open Trajectory metric specification. The specification
requires `streaming` on a provider attempt (`streaming: null` or a missing flag is
`required_field_missing`; see its `streaming-null` conformance case), so a caller always states it,
`false` for a non-streaming call. The library does not default it.

Usage formats are `auto`, `openai_chat`, `openai_responses`, `anthropic`,
`gemini` and `gemini_openai_compat`.

## Example

```c
#include "ai_usage.h"

const char *request =
    "{\"profile\": \"gen_ai.client.provider_attempt@0.1.0\","
    " \"observation\": {\"operation_name\": \"chat\", \"provider_name\": \"openai\","
    " \"duration_seconds\": 0.4, \"streaming\": false, \"observation_point\": \"gateway\"}}";

ddog_ai_usage_Batch *batch = NULL;
ddog_ai_usage_batch_new(&batch);

ddog_ai_usage_Buffer out = {0};
if (ddog_ai_usage_batch_add(batch, (const uint8_t *)request, strlen(request), &out) !=
    DDOG_AI_USAGE_STATUS_OK) {
  /* out holds {"error": {"code", "message"}} */
}
ddog_ai_usage_buffer_drop(&out);

/* At each flush: {"datagrams": [...]}, each ready for one send. */
ddog_ai_usage_batch_take_dogstatsd(batch, (const uint8_t *)"env:prod", 8,
                                   ddog_ai_usage_UDP_MAX_PAYLOAD, &out);
ddog_ai_usage_buffer_drop(&out);
ddog_ai_usage_batch_drop(batch);
```

## Release builds

The workspace's `release` profile keeps line tables (`debug = "line-tables-only"`) for every
crate, and libdatadog's own packaging splits them off with `objcopy` afterwards; the profile is
shared, so this crate does not change it. On Linux the line tables stay in the library (an
unstripped `cdylib` is about 6.7 MB; a macOS `dylib`, which keeps them apart, about 1 MB), so a
gateway that ships the library on its own strips it after building:

```sh
cargo build --release -p libdd-ai-usage-ffi
strip --strip-debug target/release/libdd_ai_usage_ffi.so   # macOS: strip -S ...dylib
# or, without a separate step:
CARGO_PROFILE_RELEASE_STRIP=debuginfo cargo build --release -p libdd-ai-usage-ffi
```

## Header

After changing the interface, regenerate the header:

```sh
UPDATE_HEADER=1 cargo test -p libdd-ai-usage-ffi --test header
```

# libdd-ai-usage-ffi

A C interface to [`libdd-ai-usage`](../libdd-ai-usage), so that an LLM gateway
or integration in any language emits the same usage and cost metrics from the
same provider responses: Go through dlopen, Lua through LuaJIT's FFI, Python
through ctypes or a native module. Rust callers use `libdd-ai-usage` directly.

The header is [`include/ai_usage.h`](include/ai_usage.h), generated by cbindgen.
The crate builds a `cdylib` and a `staticlib`, and depends on nothing but
`libdd-ai-usage` and `serde_json`, so it can be built and loaded on its own.
The artifacts are named for the C prefix: `libdd_ai_usage_ffi.so`
(`libdd_ai_usage_ffi.dylib` on macOS, `dd_ai_usage_ffi.dll` on Windows) and
`libdd_ai_usage_ffi.a`.

## Conventions

- Structured values are UTF-8 JSON. Every input is a pointer and a length. DogStatsD comes out as
  text with no JSON: `_batch_take_dogstatsd_text` writes datagrams (lines joined by `\n`)
  separated by a NUL byte, with no trailing NUL. On failure it still writes the JSON error.
- Output is written to a `ddog_ai_usage_Buffer` the caller passes by pointer and releases with
  `ddog_ai_usage_buffer_drop`. No structure is passed by value.
- Every call returns a `ddog_ai_usage_Status`: `OK`, `REJECTED` (the input broke a rule; a JSON
  output holds `{"error": {"code", "message"}}` with a stable code) or `INTERNAL` (a null
  pointer, or a panic that was caught; a panic never crosses the boundary).
- Numbers in JSON are IEEE 754 doubles, read and written as the shortest text that round-trips.
  A caller's encoder must write doubles with up to 17 significant digits, or a cost or duration
  arrives as a nearby value, not the one measured. LuaJIT's lua-cjson defaults to 14 digits
  (OpenResty's to 16): call `cjson.encode_number_precision(17)` before encoding a request. Token
  counts are whole numbers up to 2^53 - 1 and are exact at any precision that writes them in
  full; a count written in exponent form (`1e+15`) is still read as a whole number.
- As in the rest of libdatadog, the C ABI carries no backward-compatibility guarantee across
  releases: pin a version.

## Functions

| Function | Does | Called by |
| --- | --- | --- |
| `ddog_ai_usage_project` | One observation (`{profile, observation, deployment_attributes, metrics}`) to its Datadog series and issues | AI Gateway, OpenRouter |
| `ddog_ai_usage_known_metrics` | The metric names of a profile, or of every profile for an empty one: what a request's `metrics` list can keep | AI Gateway, OpenRouter |
| `ddog_ai_usage_batch_new` / `_drop` / `_is_empty` / `_len` | A batch of projections over an export window. `_len` is the number of points held (one per Counter series, one per Histogram sample), for a flush threshold; not a line count | Kong, internal AI Gateway |
| `ddog_ai_usage_batch_add_request` | One request's documents (a JSON array: its provider attempts, token breakdowns and gateway request) added together: all or none, so a full batch drops whole requests and never keeps an attempt without its breakdown. A rejected document rejects the request. `out` may be null | Kong, internal AI Gateway |
| `ddog_ai_usage_batch_set_metrics` | The metric list kept of every document that states none. **`[]` keeps no metric**, as a document's `"metrics": []` does; `null` keeps every metric again | Kong, internal AI Gateway |
| `ddog_ai_usage_batch_set_max_len` / `_dropped` | Bound a batch to a number of points (0 lifts it). A request that does not fit is dropped whole and counted; the count only grows (taking keeps it and the bound) | Kong, internal AI Gateway |
| `ddog_ai_usage_batch_take_dogstatsd_text` | Take the batch as NUL-separated DogStatsD datagrams of at most a given size, with constant tags. A line longer than the size goes alone in a datagram of its own; only one longer than 8192 bytes (`MAX_LINE_BYTES`) is dropped and counted in the optional `dropped_lines` | Kong, internal AI Gateway |
| `ddog_ai_usage_batch_take_series` / `_set_writer` | Take the batch as metrics intake takes it from a writer that submits to the API: Counters as RATE points over the interval (aggregation SUM), distributions as intake `sketchpb.Sparse` sketches (base64), every point at a second no earlier take used, tags sorted with the writer's `host.name` and `process.pid` | AI Gateway, OpenRouter |
| `ddog_ai_usage_parse_provider_response` / `_with` | A whole provider response body (JSON, or buffered server-sent events) to the observation's usage members, the model and service tier, how it ended, its `error.type`, and the provider's own error code and message (control characters removed, cut to 256 bytes). `issues` says why something reported was not kept (`service_tier_dropped`, `response_model_dropped`). `_with` and `INCLUSIVE_TOTALS` report usage with cache and reasoning added into the input and output totals, for a caller that prices them | AI Gateway, OpenRouter, Kong |
| `ddog_ai_usage_stream_new` / `_new_with` / `_feed` / `_feed_event` / `_take` / `_drop` | The same for a stream read as it passes through, in chunks that may end anywhere, or as events the caller already split. Strings longer than 1 KiB are cut as they pass; only lines that can carry usage, an error, a terminal event, or the model and tier are decoded. A stream keeps the tier a usage-bearing event names over one echoed earlier. `_take` reports and releases | AI Gateway, OpenRouter, Kong |
| `ddog_ai_usage_stream_outcome` | How a stream ended so far (`OPEN`, `COMPLETED`, `FAILED`), with no JSON: cheap enough per chunk | internal AI Gateway |
| `ddog_ai_usage_provider_name` | A gateway's or SDK's provider name to `gen_ai.provider.name` | every consumer |
| `ddog_ai_usage_error_type` / `_error_type_known` | An error name and HTTP status to `error.type`; `_known` without the `api_error` fallback for an unknown name. Names match in any case, except Google's status names (`RESOURCE_EXHAUSTED`, `UNKNOWN`, ...), which match only in upper case, so `unknown` or `not_found` is not read as one | every consumer |
| `ddog_ai_usage_operation_name` | An upstream request path (`/v1/chat/completions`, `/v1/messages`, `/v1/embeddings`, Gemini `:generateContent`, Bedrock `/converse`) to `gen_ai.operation.name` | Kong |
| `ddog_ai_usage_provider_ids` / `_provider_id_headers` | Provider response headers, Bedrock model ARNs and a Vertex AI upstream URL to the account and project attributes; the header names to fetch (text or a JSON string; other JSON is refused) | Kong, internal AI Gateway |
| `ddog_ai_usage_datadog_tag_value` | A value as Datadog stores it in a tag | AI Gateway, OpenRouter |
| `ddog_ai_usage_is_service_tier` / `_is_deployment_value` / `_is_person_identifier` | The grammars of a service tier, a deployment attribute value and `user.id` | every consumer |
| `ddog_ai_usage_buffer_drop` | Release an output buffer | every consumer |

Observations follow the profiles of the Open Trajectory metric specification. The specification
requires `streaming` on a provider attempt (`streaming: null` or a missing flag is
`required_field_missing`; see its `streaming-null` conformance case), so a caller always states it,
`false` for a non-streaming call. The library does not default it.

Usage formats are `auto`, `openai_chat`, `openai_responses`, `anthropic`,
`gemini`, `gemini_openai_compat` and `bedrock_converse`. A stream or body that starts with a NUL
byte is read as an AWS event stream (Bedrock ConverseStream and InvokeModelWithResponseStream), any
other as JSON or server-sent events.

## Example

```c
#include "ai_usage.h"

const char *request =
    "{\"profile\": \"gen_ai.client.provider_attempt@0.1.0\","
    " \"observation\": {\"operation_name\": \"chat\", \"provider_name\": \"openai\","
    " \"duration_seconds\": 0.4, \"streaming\": false, \"observation_point\": \"gateway\"}}";

ddog_ai_usage_Batch *batch = NULL;
ddog_ai_usage_batch_new(&batch);

ddog_ai_usage_Buffer out = {0};
/* One request: a JSON array of its documents. */
char documents[1024];
snprintf(documents, sizeof documents, "[%s]", request);
if (ddog_ai_usage_batch_add_request(batch, (const uint8_t *)documents, strlen(documents), &out) !=
    DDOG_AI_USAGE_STATUS_OK) {
  /* out holds {"error": {"code", "message"}} */
}
ddog_ai_usage_buffer_drop(&out);

/* At each flush: datagrams separated by NUL, each ready for one send. */
size_t dropped = 0;
ddog_ai_usage_batch_take_dogstatsd_text(batch, (const uint8_t *)"env:prod", 8,
                                        ddog_ai_usage_UDP_MAX_PAYLOAD, &dropped, &out);
ddog_ai_usage_buffer_drop(&out);
ddog_ai_usage_batch_drop(batch);
```

## Cost

`cargo run --release -p libdd-ai-usage-ffi --example hot_paths` prints the time and allocations of
the calls a gateway makes per request.

## Release builds

The workspace's `release` profile keeps line tables (`debug = "line-tables-only"`) for every
crate, and libdatadog's own packaging splits them off with `objcopy` afterwards; the profile is
shared, so this crate does not change it. On Linux the line tables stay in the library (an
unstripped `cdylib` is about 6.7 MB; a macOS `dylib`, which keeps them apart, about 1 MB), so a
gateway that ships the library on its own strips it after building:

```sh
cargo build --release -p libdd-ai-usage-ffi
strip --strip-debug target/release/libdd_ai_usage_ffi.so   # macOS: strip -S ...dylib
# or, without a separate step:
CARGO_PROFILE_RELEASE_STRIP=debuginfo cargo build --release -p libdd-ai-usage-ffi
```

## Header

After changing the interface, regenerate the header:

```sh
UPDATE_HEADER=1 cargo test -p libdd-ai-usage-ffi --test header
```
